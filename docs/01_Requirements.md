# Requirements

## 1. はじめに

本書では、食材在庫管理Webアプリケーションの要件を定義する。

まず、外部APIやAIへ依存せず、単一ユーザーがローカル環境で利用できる在庫管理アプリを完成させる。その後、レシピ管理、レシートOCR、外部API、AI・機械学習、クラウド運用を段階的に追加する。

---

## 2. システム要件

### 2.1 基本要件

- Webブラウザから利用できること
- ローカル環境で動作すること
- 食材・在庫・購入日・消費期限・買うものリストをデータベースへ保存できること
- アプリケーションを再起動しても登録内容が保持されること
- 単一ユーザーで利用できること
- ルートURL `/` に在庫一覧画面を表示すること

### 2.2 開発方針

- 小さな単位で設計・実装・確認する
- 実装難易度と利便性のバランスを取る
- 過度に複雑な機能は後回しにする
- 設計書と実装内容の整合性を保つ
- テストは重要な処理を中心に必要最小限とする

---

## 3. Phase1 機能要件

### 3.1 食材管理

- 食材を登録・編集・削除できる
- 食材名、カテゴリ、基本単位を管理できる
- 食材名は必須とする
- 同じ食材名の重複登録時には確認を表示する
- 食材名の前後空白や全角英数字などを可能な範囲で正規化する

### 3.2 在庫一覧

- 登録済み食材を一覧表示できる
- 食材名、カテゴリ、在庫数量、購入日、消費期限、単位を表示できる
- 食材名による部分一致検索ができる
- 複数カテゴリで絞り込める
- 検索とカテゴリ絞り込みを同時に使用できる
- 登録順、食材名順、カテゴリ順で並び替えられる
- 消費期限が近い順、遠い順で並び替えられる
- 消費期限未設定の食材は期限順の最後に表示する
- 在庫数量が0の食材を先頭に表示できる
- 条件を解除できる
- データがない場合にメッセージを表示する
- 複数の食材を選択して買うものリストへ追加できる

### 3.3 在庫数量管理

- 食材登録時に初期数量を設定できる
- 編集画面から数量を変更できる
- 一覧画面の「＋」「－」で数量を増減できる
- 数量は0未満にならない
- 数量は0.5刻みで管理できる
- 数量変更後も一覧の表示条件を維持する

### 3.4 カテゴリ・単位

- カテゴリと基本単位を選択式で入力できる
- 「その他」を選択した場合は任意入力できる
- 登録済みの値を編集画面で正しく再表示できる
- 自動入力された内容を利用者が変更できる

### 3.5 重複食材登録

同じ食材名がすでに登録されている場合は、次から選択できる。

- 現在の在庫数量へ今回の数量を追加する
- 現在の在庫数量を今回の数量へ変更する
- 登録をキャンセルする

購入日・消費期限が入力されている場合は、選択した処理に応じて日付も適切に反映する。

数量を追加する場合は、購入日は既存分と今回入力分のうち早い日付を保持し、消費期限は設定済みの日付のうち早い日付を保持する。

### 3.6 購入日管理

- 食材登録時に購入日を必須入力できる
- 新規登録画面では当日を初期値として表示する
- 編集画面から購入日を変更できる
- 一覧画面に日付入力欄を常時表示する
- 手入力またはカレンダーで日付を確定した時点で自動保存する
- 保存時にページ全体を再読み込みしない
- 購入日は空欄にできない
- 保存中・保存成功・保存失敗を画面上で確認できる
- 保存失敗時は入力前の日付へ戻す

### 3.7 消費期限管理

- 食材登録時に消費期限を任意入力できる
- 編集画面から期限を変更できる
- 一覧画面に日付入力欄を常時表示する
- 手入力またはカレンダーで日付を確定した時点で自動保存する
- 保存時にページ全体を再読み込みしない
- 日付を空欄にすると未設定へ戻せる
- 保存中・保存成功・保存失敗を画面上で確認できる
- 保存失敗時は入力前の日付へ戻す
- 期限切れを表示できる
- 今日から3日後までを期限間近として表示できる
- 4日後以降を通常表示とする
- 期限順で並び替えられる

### 3.8 買うものリスト

- 在庫一覧から食材を選択できる
- 複数食材をまとめて買うものリストへ追加できる
- 在庫数量が0になっただけでは自動追加しない
- 同じ食材を重複追加しない
- 買うものリストを別画面で確認できる
- 未購入・購入済みを切り替えられる
- 購入済みから未購入へ戻せる
- 項目をリストから個別削除できる
- 購入済み項目をまとめて削除できる
- 購入済みにしても在庫数量は自動加算しない
- 食材本体が削除された場合は、関連する買うものリスト項目も削除する

### 3.9 エラー処理

- 存在しない食材IDへアクセスした場合に適切な応答を返す
- 入力エラー時に修正方法が分かるメッセージを表示する
- データベース処理失敗時にアプリケーション全体を停止させない
- JavaScriptによる自動保存失敗時に画面上へメッセージを表示する

---

## 4. 非機能要件

### 4.1 操作性

- 起動直後に在庫一覧を表示する
- 日常的な操作は一覧画面から行えるようにする
- 操作回数を必要以上に増やさない
- スクロール位置や検索条件を可能な範囲で維持する

### 4.2 保守性

- ルーティング、CRUD、モデル、テンプレートの責務を分ける
- マイグレーションはAlembicで管理する
- 設計書と実装を同期する
- 未使用コードは原則削除する

### 4.3 テスト

- 個人利用・学習用途のため、網羅性より重要処理の確認を優先する
- CRUD、期限判定、期限順ソート、自動保存、購入日、買うものリストの主要処理を対象とする
- 画面の細かな見た目は手動確認を中心とする

## 5. Phase2以降

### Phase2：レシピ管理・在庫活用

- レシピ登録・編集・削除
- 必要食材登録
- 在庫との照合
- 不足食材表示
- 調理後の在庫減算
- 調理履歴

### Phase3：レシートOCR

- 画像アップロード
- 商品名・購入数量の読み取り
- 結果確認・修正
- 在庫反映

### Phase4：外部API・AI

- 外部レシピAPI
- 在庫・消費期限を考慮した提案
- AI・機械学習による推薦

### Phase5：運用・クラウド

- Docker
- PostgreSQL
- AWS
- CI/CD
- ログイン
- マルチユーザー
- スマートフォン表示改善
