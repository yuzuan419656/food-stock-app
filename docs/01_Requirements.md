# Requirements

## 1. はじめに

本書では、食材在庫管理Webアプリケーションの要件を定義する。

まず、外部APIやAIへ依存せず、単一ユーザーがローカル環境で利用できる在庫管理アプリを完成させる。その後、レシピ管理、レシートOCR、外部API、AI・機械学習、クラウド運用を段階的に追加する。

---

## 2. システム要件

### 2.1 基本要件

- Webブラウザから利用できること
- ローカル環境で動作すること
- 食材・在庫・購入日・消費期限・買うものリストをデータベースへ保存できること
- アプリケーションを再起動しても登録内容が保持されること
- 単一ユーザーで利用できること
- ルートURL `/` に在庫一覧画面を表示すること

### 2.2 開発方針

- 小さな単位で設計・実装・確認する
- 実装難易度と利便性のバランスを取る
- 過度に複雑な機能は後回しにする
- 設計書と実装内容の整合性を保つ
- テストは重要な処理を中心に必要最小限とする

---

## 3. Phase1 機能要件

### 3.1 食材管理

- 食材を登録・編集・論理削除できる
- 食材名、カテゴリ、基本単位を管理できる
- 食材名は必須とする
- 同じ食材名の重複登録時には確認を表示する
- 食材名の前後空白や全角英数字などを可能な範囲で正規化する
- 削除済み食材は通常の一覧・検索・選択候補から除外する
- 削除時も食材レコードと在庫ロットを保持する
- 削除済み食材への編集・在庫操作を禁止する
- 削除済み食材と同じ名前を登録した場合は復元確認を表示する
- 復元時は同じ食材IDと過去の在庫ロットを再利用する
- 復元時に入力された数量は新しい在庫ロットとして追加する
- 既存と異なる単位では復元できない

### 3.2 在庫一覧

- 登録済み食材を一覧表示できる
- 食材名、カテゴリ、在庫数量、購入日、消費期限、単位を表示できる
- 食材名による部分一致検索ができる
- 複数カテゴリで絞り込める
- 検索とカテゴリ絞り込みを同時に使用できる
- 登録順、食材名順、カテゴリ順で並び替えられる
- 消費期限が近い順、遠い順で並び替えられる
- 消費期限未設定の食材は期限順の最後に表示する
- 在庫数量が0の食材を先頭に表示できる
- 条件を解除できる
- データがない場合にメッセージを表示する
- 複数の食材を選択して買うものリストへ追加できる

### 3.3 在庫数量・ロット管理

- 食材登録時に初期数量を設定できる
- 在庫は購入日・消費期限別のロットとして管理する
- 1つの食材に複数の在庫ロットを登録できる
- 食材編集画面からロット一覧を確認できる
- ロットごとに数量、購入日、消費期限を編集できる
- ロットを個別に論理削除できる
- 一覧画面には有効なロットの合計数量を表示する
- 一覧画面の「＋」で最も新しく購入した有効ロットへ0.5追加する
- 追加対象のロットがない場合は新規ロット登録画面を表示する
- 一覧画面の「－」で消費期限が近いロットから0.5減算する
- 消費期限未設定の場合は購入日が古いロットから減算する
- 数量は0未満にならない
- 数量は0.5刻みで管理できる
- 数量変更後も一覧の表示条件を維持する

### 3.4 カテゴリ・単位

- カテゴリと基本単位を選択式で入力できる
- 「その他」を選択した場合は任意入力できる
- 登録済みの値を編集画面で正しく再表示できる
- 自動入力された内容を利用者が変更できる

### 3.5 重複食材登録・復元

有効な同名食材が登録されている場合は、次から選択できる。

- 既存食材へ今回の数量を新しい在庫ロットとして追加する
- 既存食材の情報を今回の入力内容で上書きする
- 登録をキャンセルする

削除済みの同名食材が登録されている場合は、次から選択できる。

- 削除済み食材を復元する
- 登録をキャンセルする

復元時は次のルールを適用する。

- 新規食材レコードを作成せず、既存の食材IDを再利用する
- 過去の在庫ロットを保持する
- 今回の数量が0より大きい場合は新しいロットとして追加する
- 既存食材と今回入力した単位が異なる場合は復元できない
- 買うもの追加画面から遷移した場合は、復元後に買うものリストへ追加する

### 3.6 購入日管理

- 食材登録時に購入日を必須入力できる
- 新規登録画面では当日を初期値として表示する
- 編集画面から購入日を変更できる
- 一覧画面に日付入力欄を常時表示する
- 手入力またはカレンダーで日付を確定した時点で自動保存する
- 保存時にページ全体を再読み込みしない
- 購入日は空欄にできない
- 保存中・保存成功・保存失敗を画面上で確認できる
- 保存失敗時は入力前の日付へ戻す

### 3.7 消費期限管理

- 食材登録時に消費期限を任意入力できる
- 編集画面から期限を変更できる
- 一覧画面に日付入力欄を常時表示する
- 手入力またはカレンダーで日付を確定した時点で自動保存する
- 保存時にページ全体を再読み込みしない
- 日付を空欄にすると未設定へ戻せる
- 保存中・保存成功・保存失敗を画面上で確認できる
- 保存失敗時は入力前の日付へ戻す
- 期限切れを表示できる
- 今日から3日後までを期限間近として表示できる
- 4日後以降を通常表示とする
- 期限順で並び替えられる

### 3.8 買うものリスト

- 在庫一覧から複数食材をまとめて追加できる
- 買うものリスト画面から追加画面へ遷移できる
- 食材名の検索と複数カテゴリによる絞り込みができる
- 絞り込み結果から複数食材をまとめて追加できる
- 食材マスタにない項目を手入力で追加できる
- 買うもの追加画面から新しい食材を登録できる
- 新しい食材の登録と同時に買うものリストへ追加できる
- 同じ食材や同じ手入力項目を重複追加しない
- 在庫数量が0になっただけでは自動追加しない
- 未購入・購入済みを切り替えられる
- 購入済みから未購入へ戻せる
- 項目をリストから個別削除できる
- 購入済み項目をまとめて削除できる
- 購入済みにしても在庫数量は自動加算しない
- 食材が論理削除されても既存の買うものリスト項目は保持する
- 論理削除済み食材は新しい追加候補から除外する

### 3.9 エラー処理

- 存在しない食材IDへアクセスした場合に適切な応答を返す
- 入力エラー時に修正方法が分かるメッセージを表示する
- データベース処理失敗時にアプリケーション全体を停止させない
- JavaScriptによる自動保存失敗時に画面上へメッセージを表示する

---

## 4. 非機能要件

### 4.1 操作性

- 起動直後に在庫一覧を表示する
- 日常的な操作は一覧画面から行えるようにする
- 操作回数を必要以上に増やさない
- スクロール位置や検索条件を可能な範囲で維持する

### 4.2 保守性

- ルーティング、CRUD、モデル、テンプレートの責務を分ける
- マイグレーションはAlembicで管理する
- 設計書と実装を同期する
- 未使用コードは原則削除する

### 4.3 テスト

- 個人利用・学習用途のため、網羅性より重要処理の確認を優先する
- CRUD、期限判定、期限順ソート、自動保存、購入日、買うものリストの主要処理を対象とする
- 画面の細かな見た目は手動確認を中心とする

## 5. Phase2以降

- 不足食材表示
- 調理後の在庫減算

- 在庫・消費期限を考慮した提案
- AI・機械学習による推薦

### Phase5：運用・クラウド

- Docker
- PostgreSQL
- AWS
- CI/CD
- ログイン
- マルチユーザー
- スマートフォン表示改善
