# food-stock-app 開発引き継ぎ資料

## 1. この資料の目的

本資料は、家庭向け食品在庫管理Webアプリ `food-stock-app` の開発状況・設計方針・実装済み機能・今後の開発予定をまとめた引き継ぎ資料である。

以下の2つを別の開発者またはAIに渡すことで、現在の開発者とほぼ同じ前提で開発を継続できることを目的とする。

コードの実際の状態についてはGitHubを最終的な正とし、本資料は「設計意図」「仕様」「開発方針」「今後の予定」を補完するものとして使用する。

---

# 2. プロジェクト概要

## 2.1 アプリ名

`food-stock-app`

## 2.2 目的

家庭内の食品在庫を管理し、以下を実現する。

- 食品の重複購入防止
- 賞味期限・消費期限切れの防止
- 食品ロスの削減
- 現在の在庫から作れる料理の把握
- レシピに必要な不足食材の把握
- レシピを作った際の在庫自動減算
- 在庫状況・期限・調理履歴を利用したレシピ推薦
- 将来的にはレシートOCRによる在庫登録自動化

単純なCRUDアプリではなく、

**在庫管理 → レシピ管理 → 在庫消費 → 履歴 → レコメンド → OCR**

という流れで段階的に発展させる。

# 4. 基本的な開発方針

## 4.1 小さい単位で実装する

一度に大きな機能を実装しない。

原則として、

1. 1つの機能を決める
2. 専用ブランチを作成
3. 実装
4. テスト
5. ブラウザで手動確認
6. commit
7. push
8. 次の機能へ進む

という流れで進める。

---

## 4.2 ブランチ単位

基本的に、

`feature/機能名`

の形式を使用する。

例：

```text
feature/recipe-serving
feature/recipe-consumption
feature/cooking-history
feature/recipe-recommendation
feature/receipt-ocr
```

バグ修正の場合は必要に応じて、

```text
fix/xxx
```

を使用する。

# 5. AIに開発を依頼するときの重要ルール

別のAIが開発を継続する場合、以下のルールを守ること。

## 5.1 既存コードを最初に確認する

新機能を実装する前に必ず、

- models
- crud
- services
- routers
- templates
- static
- tests

の関連コードを確認する。

既存の構造を無視して新しい実装方式を持ち込まない。

---

## 5.2 既存設計との整合性を優先する

アプリはすでに複数機能が実装されているため、

「一般的にはこちらの設計が良い」

という理由だけで既存構造を大規模変更しない。

必要な場合は、

- なぜ変更するのか
- 変更範囲
- 既存機能への影響

を明示してから実施する。

---

## 5.3 service層を活用する

複雑なビジネスロジックはrouterへ直接書きすぎない。

基本的な役割分担は以下。

### router

- HTTPリクエスト受付
- フォーム値取得
- service呼び出し
- templateへ値を渡す
- redirect

### crud

- DBへの基本操作
- SELECT
- INSERT
- UPDATE
- DELETE

### service

- 在庫減算
- 人数換算
- 推薦スコア
- OCR結果処理
- 複数テーブルを使う処理

などのビジネスロジック。

---

## 5.4 テストを必ず追加する

機能追加時は可能な限りpytestを追加する。

最低限、

- 正常系
- 境界値
- エラーケース

を検討する。

---

## 5.5 HTML修正時の回答方法

AIがHTMLファイルを修正する場合は、

**差分だけではなく、修正後のHTMLファイル全体を出力する。**

CSSやPythonについては変更内容に応じて差分または必要部分でもよいが、HTMLについては原則全文を提示する。

# 9. IngredientとInventoryの考え方

食材そのものと在庫情報を分離する。

概念的には、

```text
Ingredient
    1
    |
    N
Inventory
```

となる。

Ingredientは、

「卵」

「牛乳」

「玉ねぎ」

などの食材マスター的情報。

Inventoryは、

- 購入日
- 賞味期限
- 数量

などの実在庫情報を保持する。

---

# 10. 在庫ロット

同じ食材でも購入日や期限が異なる場合があるため、在庫は複数ロットを扱う。

例：

```text
卵

ロット1
購入日：8/1
期限：8/10
数量：6

ロット2
購入日：8/5
期限：8/15
数量：10
```

在庫を減らす場合は原則、

**期限が近いロットから使用する。**

# 24. 人数換算

## 状態

**直近で実装・動作確認済みの機能**

レシピに登録された基準人数に対し、

```text
1人分
2人分
3人分
4人分
...
```

のように人数を変更すると、必要食材量を換算する。

例：

2人分として、

```text
玉ねぎ 1個
肉 200g
```

と登録されている場合、

4人分なら、

```text
玉ねぎ 2個
肉 400g
```

として表示する。

この処理はservice層へ分離する方向で実装している。

直近の作業では、

```text
app/services/recipe_serving.py
tests/services/test_recipe_serving.py
```

が追加され、

関連して、

```text
app/routers/recipes.py
app/templates/recipes/detail.html
app/static/css/style.css
tests/routers/test_recipes.py
```

が変更されている。

確認時点では、

```text
tests/routers/test_recipes.py
25 passed
```

全体では、

```text
216 passed
```

を確認している。

また、

```bash
git diff --check
```

でも問題がないことを確認済み。

ブラウザ上でも見た目・動作ともに問題ないことを確認している。

ただし、引き継ぎ時にはGitHubの最新commitを確認し、この変更がpush済みかどうかを必ず確認すること。

---

# 25. 人数換算の基本ルール

人数変更は、

```text
換算後数量
=
基準数量 × 選択人数 / 基準人数
```

で計算する。

DB内の元レシピ数量を書き換えてはいけない。

表示時または調理処理時に換算する。

# 27. レシピ調理・在庫減算機能

## 目的

レシピ詳細画面で、

```text
このレシピを作る
```

等の操作を行った際、必要材料を在庫から減らす。

---

# 28. 在庫確認

例：

レシピ：

```text
カレー 2人分

玉ねぎ 2個
にんじん 1本
肉 300g
```

在庫：

```text
玉ねぎ 3個
にんじん 0.5本
肉 500g
```

なら、

```text
玉ねぎ：足りる
にんじん：0.5本不足
肉：足りる
```

と判定する。

---

# 29. 単位

自動減算は、

**レシピと在庫で単位が一致する場合を基本とする。**

例：

```text
レシピ：牛乳 200 ml
在庫：牛乳 1000 ml
```

なら自動計算可能。

一方、

```text
レシピ：玉ねぎ 100 g
在庫：玉ねぎ 1 個
```

のような場合、自動換算しない。

重量と個数の換算には食材ごとの換算情報が必要になるためである。

この場合は、

- 警告表示
- ユーザーによる手動判断

とする。

将来的に換算テーブルを導入する余地はある。

---

# 30. 不足時の処理

在庫不足でも完全に調理操作を禁止しない。

例：

必要：

```text
牛乳 300ml
```

在庫：

```text
牛乳 200ml
```

の場合、

不足を警告した上で、

```text
在庫の200mlだけ消費
```

することを可能にする。

つまり、

**部分消費を許可する。**

---

# 31. 在庫の消費順序

レシピによる減算でも通常の在庫減算と同じく、

**期限の近い在庫ロットから使用する。**

---

# 32. 調理処理で重要なこと

複数食材を同時に変更するため、

可能な限り1トランザクションとして扱う。

途中で例外が発生した場合に、

```text
玉ねぎだけ減った
肉は減っていない
```

のような中途半端な状態にならないよう注意する。

---

# 50. OCRの目的

スーパー等のレシート画像から、

```text
購入商品
数量
購入日
```

などを読み取り、

food-stock-appの在庫登録候補として利用する。

---

# 51. OCR処理の考え方

OCRだけで直接DBへ登録しない。

推奨フローは、

```text
レシート画像
    ↓
画像前処理
    ↓
OCR
    ↓
文字列
    ↓
商品名・数量などを解析
    ↓
登録候補
    ↓
ユーザー確認・修正
    ↓
在庫へ登録
```

とする。

OCR誤認識があるため、

**必ず確認画面を挟む。**

---

# 52. OCRアプリとの責務分離

将来的にOCR機能を独立させる可能性がある。

OCR側は、

```text
画像/PDF
↓
文字認識
↓
構造化候補
```

までを担当し、

food-stock-app側は、

```text
OCR結果
↓
```

# 63. 開発上の最重要方針

このアプリでは、

**機能を増やすことよりも、現在ある機能を壊さずに少しずつ完成させることを優先する。**

```text
在庫
↓
レシピ
↓
在庫減算
↓
履歴
↓
推薦
```

は相互に依存するため、前の段階を十分にテストしてから次へ進む。

また、OCRや機械学習など目立つ機能を先に実装せず、

**まずデータ構造と基本的な業務ロジックを完成させる。**

これがこのプロジェクトの基本方針である。
